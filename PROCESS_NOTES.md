# Process notes

## Stage 1: seeded data generator
- Built `scripts/generate-data.ts` (mulberry32, seed 20261020, run with `npm run generate-data`) → 14 table JSONs + `meta.json` in `src/data/` (~1.5 MB). It generates random history (1,246 Asia enquiries / 523 deals; 441 / 223 for Rotterdam), then tunes S1 (DPD ≈ 4, claim share exactly 3× the desk, exposure $3.92M + $0.40M, average premium $10) and asserts every S1–S4 figure, so a seed change can't silently break the demo. Two runs produce byte-identical output.
- Dead end: the first pass gave 4 customers credit limits of $13–20M (heavy traders on 45-day terms in both BUs). Fixed by dropping 45-day terms, narrowing the activity spread, capping limits at $10M, and seeding today's generic queue only from customers under $6M exposure, so S1 stays the only credit counter. Known quirk: the lowest lost premium on S1's similar deals is $3 (random loss at the floor). It's left as generated.
- Assumptions: the demo clock is frozen at `2026-10-20T09:00+08:00` (`meta.now`); one delivery per barge per day; declined enquiries have `outcome = lost`; status is `open/quoted/countered/declined`; exposure = unpaid invoices + undelivered deal value (qty × price). Rotterdam's port is the fictional "North Sea Hub" (no real port names). Fake IMOs use a deliberately invalid check digit. `agg_customer_exposure` has today's snapshot only.

## Stage 2: semantic layer
- Added `src/semantic/`: `metrics.ts` is a typed registry of 40 entries, each with definition, formula, owner, certification, source tables, scope and roles. 30 are single numbers, statuses or flags; 10 are governed datasets (queue, barge timeline, win range, suggested move, the AI "Ask" series). `permissions.ts` builds the user's row- and object-level scoped view. `query.ts` is the only read path, returning `{ value, metricId, asOf, restricted? }`. Only `permissions.ts` imports the raw `warehouse.ts`, so the "same definitions, same permissions" claim holds in the code, not only in the UI.
- Verified with a throwaway script (bundled with `vite build --ssr`, not committed) that drives the demo script through `query()`: S1 COUNTER 1,100 mt at $13 and −$247k headroom; S2 COUNTER to 26 Oct on Corvana Gannet; S3 BLOCKED last; S4 QUOTE at $13.50; exact Rotterdam refusal wording. Queue mix: 33 QUOTE, 4 COUNTER, 2 DECLINE, 1 BLOCKED. One plain enquiry (margin DECLINE) sits between S1 and S2.
- Changed the plan: metrics call shared helper functions rather than calling `query()` recursively; that avoided a circular type and keeps one permission check per request. Refusals come from the permission layer (an explicit `businessUnit` param, or a row outside scope), not from AI templates, so the AI can't word around them.
- Assumptions: the barging estimate for an open enquiry is the desk's 12-month average barging cost per mt; "12 months" filters deals on delivery date and includes contracted, undelivered deals; max quantity rounds down to 50 mt; the shorter-terms counter option is fixed at 15 days; the clock is `meta.now`. Trader status changes (stage 5) aren't modelled yet.

## Stage 5: quote builder + actions
- Quote builder: a premium slider in Pricing & Margin whose track carries the win range (won p25–p75 band, lowest-lost tick, suggested tick, n). The trader's terms live in one `EnquiryWorkspace` state and feed `query()`, so the price, margin and the Compliance & Credit headroom all move together (S1: −$247k at $13 → −$250k at $15; 12–28 ms per tick). Counter opens a form prefilled from the suggested move: S1 offers 1,100 mt / full 1,500 mt with letter of credit / 15-day terms (with the brief's caveat); S2 prefills Mon 26 Oct on Gannet. Decline takes a reason (default mapped from the rule) with a tooltip on why reasons matter. Every action goes through a review modal → Send → toast, and the queue re-ranks.
- Governance for writes: `semantic/actions.ts` is the only write path. It checks scope (another BU's enquiry gets the same restricted sentence), refuses any response on a compliance FLAG, refuses double sends, then writes through `permissions.writeEnquiryResponse`, which bumps a data version the UI subscribes to. Tested outside the UI with a throwaway script. Letter of credit is in the headroom metric's definition and formula (deal uses no customer credit), not a UI special case.
- Fixed while testing: the blocked S3 button read "Quote at $9.00" (a price on a blocked enquiry) and Decline was enabled (a draft on a blocked enquiry). Both are now disabled and the write path rejects them too. The header kept counting down after a response; it now shows "Response sent · Countered". Dropped a `useMemo` that oxlint rightly flagged; the data subscription re-renders the queue.
- Assumptions / gaps: the modal's message box is empty for now (the AI draft is stage 6). Counter quantity, date and payment terms aren't stored (fct_enquiry has no columns for them; one quote round per the data model), so reopening a countered enquiry shows the original quantity. Responses live in memory until reload, per "no real persistence". Stage 5 is on branch `claude/stage-5-quote-actions` so PR #4 stays reviewable.

## Stage 6: AI moments (deterministic)
- `src/ai/` holds the three moments as templates over `query()` results; they import nothing but the query layer and formatters. Text is a list of segments (strings or governed values), so every figure renders as a clickable metric chip and each output carries a "Based on:" line. (1) Brief: 1–3 sentences per suggested move/reason. S1 names late payment and claims as premium adjustments and credit headroom as the reason to counter; S2 points to Gannet on Mon 26 Oct; S3 says only "Refer to compliance". (2) Ask: inline box with three question pills and seven intents (why this premium, benchmark 30d, premium trend by month, last 5 deals, claims, credit exposure, plus other-BU). Answers come with a table or a mini SVG chart. (3) Draft: the send modal opens with a message built only from the trader's terms; decline drafts never reveal the internal reason.
- The Rotterdam refusal isn't AI wording: the question is turned into `query(..., { businessUnit: 'BU_ROTTERDAM_BUNKERING' })`, and the permission layer returns the same sentence as the restricted exposure line.
- What I caught by testing: "What will the benchmark be next week?" first matched the benchmark-history intent, which answers a different question. Forecast and what-if questions now get "I can only answer from governed metrics". "Benchmark trend" was also at risk of matching the premium-trend intent, so intents were reordered. A scan of all 40 briefs plus the pill answers found deal and claim counts typed as plain text; they're chips now. The only literal numbers left are rule constants ($2, $1, $3/mt, $0.50, 12-month, more than 3 days).
- Assumptions: intent matching is keyword-based by design (deterministic, demo-safe); no LLM stretch. The brief uses the quantity from enquiry details as a chip whose card is "Enquiry details", which is honest but less specific than a dedicated metric.
